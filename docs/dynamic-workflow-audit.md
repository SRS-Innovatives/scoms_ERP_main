# SCOMS Dynamic Workflow Audit Report — Phase 2 Refresh

Generated 2026-09-20. Scope: full repo (4 backend services, 4 frontend apps, shared lib, Prisma schema/DB). This document **supersedes the 2026-08-25 version** (`git log` shows dozens of commits and thousands of changed lines in the intervening ~4 weeks). Every claim below was re-verified against the current working tree by reading the cited file — nothing was carried forward from the old document without independent re-checking. **At a glance**: of the original 9 priority-ordered fixes, **7 are now resolved** (mock-data purge across all 4 frontends, both IDOR gaps, real Razorpay signature verification, Announcement/Notification APIs, Semester/Section/Subject CRUD, Super Admin's four previously-fully-mocked controllers, and the four "dead button" UI stubs). **2 remain partially open** (JWT default-secret fallback is fixed but the `UnifiedLoginPage` demo-credential/`demo_access_token` pattern is not; the RBAC/Permission-Matrix wiring is real end-to-end for enforcement but has a newly-discovered gap — see §8). A significant **new** issue not present in the original audit was found in the Permission Matrix: it now persists edits to a real table, but the enforcement engine never reads that table, so editing permissions in the UI has zero effect on real authorization decisions (§8, §15 item 1).

## 8. Authorization Problems

**Substantially rearchitected since the last audit — mostly resolved, but with one significant newly-discovered gap.**

- `shared/middleware/shadowPermission.js:1-70` is real, and is now genuinely gating requests, not just logging: when `RBAC_ENFORCEMENT_ENABLED=true` (confirmed set in `.env:25`; `.env.example:19` still defaults it to `false`, which is the correct posture for a template), a permission `DENY` throws `AuthorizationError` (403) via `:34-36`, instead of the shadow-mode audit-log-only path used when the flag is off (`:38-56`). Route coverage: `shadowPermission(...)` now appears **185** times in `IntituteAdmin_Backend/src/routes/apiRoutes.js` (357 route definitions total), **64** times in `Staff_backend/src/routes/apiRoutes.js` (92 routes), **49** times in `SuperAdmin_Backend/src/routes/apiRoutes.js` (103 routes), and **14** times in `Student_Backend/src/routes/apiRoutes.js` (67 routes). The lower Student/SuperAdmin coverage ratios were not further investigated for whether the remaining routes are intentionally covered by coarser `requireRole` guards instead (plausible, e.g. `SuperAdmin_Backend/src/routes/apiRoutes.js:43` gates the whole router behind `requireRole(SUPER_ADMIN, PLATFORM_ADMIN)` before any per-route `shadowPermission` even runs) — flagged as **not fully verified**, not as a confirmed gap.
- `shadowPermission.js:4-18`'s own header comment states only `TEACHER` and `INSTITUTE_ADMIN` have been exercised against the matrix with real live traffic as of authoring; the other roles are "matrix-only, never enforced" in practice, per that same comment — worth taking at face value rather than assuming full production-readiness across all 11+ roles.
- **New finding, not in the original audit**: `SuperAdmin_module_forntend`'s Permission Matrix page (`PermissionMatrixPage.jsx:202`, `userService.updateRolePermissions(selectedRole, permissions)`) now really persists to `SuperAdmin_Backend/src/controllers/userController.js:163-189`, which upserts a `RolePermissionOverride` row (§3 above). **But** `shared/permissions/permissionMatrix.js:252-256`'s `hasPermission(userRole, requiredPermission)` — the function `shadowPermission.js:24` actually calls to decide allow/deny — is a **synchronous, pure function that reads only the static in-code `ROLE_PERMISSIONS` object** (`:252-256`); it never queries `RolePermissionOverride`. So today, editing and saving permissions in the Permission Matrix UI writes a real row to a real table with a real audit log entry, giving every appearance of working, but has **zero effect** on what `shadowPermission` actually allows or denies at runtime — the override table is write-only. This is a materially different (and more deceptive) bug than the old "no-op echo" — the old bug was obviously broken (nothing persisted); this one looks fixed but isn't wired end-to-end.
- The old CreateRoleModal dead-button concern from the prior audit **no longer applies as a bug**: no `CreateRoleModal.jsx` file exists anywhere in the repo (confirmed via `find`), and `RolesListPage.jsx:33-41` explicitly presents roles as a fixed, read-only list (`subtitle: "Fixed system roles and their real-time user assignments — permissions per role are edited in the Permission Matrix"`) with an "Edit Permissions" action that navigates to the real Permission Matrix page rather than any create-role flow. This matches the deliberate-redesign explanation, not an unfixed stub — though see the bullet above for the real issue that redesign now has.

## 12. Module Integration Problems

**Largely resolved across all three previously-"island" portals**, based on the service-call counts gathered in §1: **134/170** Institute Admin pages, **77/100** Staff pages, and **42/51** Student pages now call a `*Service` module rather than reading only from static mock data. This is a wholesale reversal of the prior audit's 2/119, 0/92, and 16/53-mock findings.

- The specific example cited in the old report — Institute Admin's `StudentListPage.jsx` never re-fetching from the API — is fixed: `StudentListPage.jsx:21-25` now calls a real service inside a `useEffect`-driven load function.
- **A new, narrower issue was found in its place** (not present in the old audit, because the old audit never got past "the page doesn't call the API at all"): `StudentListPage.jsx:24-25` uses the pattern `.catch((err) => notifyError(...)).finally(() => setLoading(false))` with **no separate error-state tracked** — on a failed fetch, `loading` becomes `false` and the page falls through to whatever it renders for an empty/default list state, indistinguishable from "this institution genuinely has zero students." A toast fires (`notifyError`), but there is no in-page retry affordance and no way to tell, from the rendered page alone, "the request failed" apart from a transient toast. The `SuperAdmin_module_forntend`/`Student_module_frontend` portals were recently given a dedicated `ErrorState` component to fix exactly this class of bug (see §15), but **`IntituteAdmin_module_frontend` and `Staff_module_frontend` were not part of that pass**: both portals do have an `ErrorState.jsx` component file (`IntituteAdmin_module_frontend/src/components/common/ErrorState.jsx`, `Staff_module_frontend/src/components/common/ErrorState.jsx`), but a grep for actual usages of the component anywhere in either portal's pages returns **zero** — the component exists but is imported nowhere. A rough count of pages following the same `catch(...).finally(() => setLoading(false))` shape without a companion error-state variable found **90** matches under `IntituteAdmin_module_frontend/src/Pages` and **73** under `Staff_module_frontend/src/pages` (this count is a heuristic grep for the pattern text, not a manual per-file confirmation of every match, so treat it as an order-of-magnitude estimate, not an exact page count).
- The `Student_module_frontend` real-services-but-dead-code finding from the old audit is resolved: the assignment/attendance/fee/student services are now actively imported (42/51 pages), and the `ErrorState` wiring pass (~53 pages across SuperAdmin + Student) was spot-checked directly on `Student_module_frontend/src/pages/assignments/AssignmentDetailPage.jsx`, which both imports `assignmentService` (`:8`) and has a real submission form wired to `assignmentService.submit({ assignmentId, content, fileUrl })` (`:63`) with a `submitting` loading state (`:24,194,197`) and error toast on failure (`:70`) — this was previously dead/unused code per the task brief and is now confirmed live and functioning end-to-end as UI.

## 15. Recommended Fixes — Priority Order for Phase 3 onward

The frontend↔backend wiring work that dominated the old Phase 2 priority list is essentially done. What's left is narrower and more subtle — mostly places where something *looks* fixed but isn't fully wired, or where the fix pattern used in 2 of 4 portals wasn't extended to the other 2.

1. **Make the Permission Matrix UI actually do something.** `shared/permissions/permissionMatrix.js:252-256 hasPermission` needs to consult `RolePermissionOverride` (merge or replace the static `ROLE_PERMISSIONS[userRole]` list with any persisted override for that role) before `shadowPermission.js` decides allow/deny. This is the single most misleading gap in the repo right now: the UI, the persistence, and the audit trail all look complete, but the actual authorization decision still comes from code that was never told the override table exists. Low-risk, well-scoped fix — one function, one query, cached/memoized if needed for request-hot-path performance.
2. **Extend the `ErrorState` wiring pass to `IntituteAdmin_module_frontend` and `Staff_module_frontend`.** Both portals already have the `ErrorState.jsx` component (unused) and both have ~70-90 pages following the same `catch(...).finally(() => setLoading(false))` pattern that silently renders an empty-list state on a failed fetch instead of a distinguishable error+retry UI — exactly the bug class the other two portals already fixed. This is now the largest remaining "looks empty vs. actually broken" ambiguity in the app.
3. **Close out the RBAC rollout for the untested roles.** Per `shadowPermission.js`'s own header comment, only `TEACHER` and `INSTITUTE_ADMIN` have been exercised against the matrix with live traffic; the other 9+ roles are enforced (since `RBAC_ENFORCEMENT_ENABLED=true` is already set repo-wide) but unvalidated against real usage. Given enforcement is already live, this is a "verify, don't just trust the matrix" task, not a "turn it on" task — audit-log review or targeted manual QA per role before calling this fully done.
4. **Reconcile or clearly separate the legacy Fee system and the Dynamic Fee Engine V2.** Both `feeController.js`/`StudentFeeAssignment` and `feeEngineController.js` are live, in the same portal, with separate frontend pages. Confirm there's no double-charge/reconciliation gap between them, or explicitly gate one behind a module flag so institutions use exactly one at a time.
5. **Decide the fate of the legacy `Institution.modules` array now that the Module Registry exists.** `resolveModules.js` already resolves both paths side-by-side; this is manageable migration debt today but will compound if new module-gated features keep needing to check both.
6. **Hygiene**: delete the now-fully-dead mock-data files (`mockData.js`, `mockStaffData.js`, `mockStudentData.js`, and the seven SuperAdmin `mock*.js` files) — confirmed zero importers repo-wide, safe to remove. Gate `UnifiedLoginPage.jsx`'s demo-credential autofill and `'demo_access_token'`/`'demo_refresh_token'` string fallbacks behind an explicit dev-only flag rather than shipping them unconditionally in shared login UI used by all four portals.
7. **Re-verify, don't assume, the items explicitly marked unverified in this document**: `shared/utils/notifications.js` simulated-send fallback (§2), `aiAssistantController.js` hardcoded-response status (§2), exam/marks-entry and payment-listing route completeness (§4), Staff dashboard aggregation (§11), `AcademicYearSetupPage.jsx`/`DepartmentSetupPage.jsx` stub status (§10), and a fresh repo-wide re-grep for `req.body.institutionId`/`req.params.institutionId`/`req.query.institutionId` (§9) to confirm the "zero matches" tenant-trust finding still holds now that dozens of new controllers exist.
8. **Add a real integration test**, not just the two hand-rolled unit-style checks that exist today. `test/tenantIsolation.test.js` and `test/rbacMatrix.test.js` (the latter is new since the last audit) both call middleware functions directly with constructed `req`/`res` objects rather than exercising a running server end-to-end (`test/rbacMatrix.test.js:14-26` sets `RBAC_ENFORCEMENT_ENABLED` in-process and invokes `shadowPermission(permission)` as a plain function, not via HTTP). Useful as fast unit coverage, but neither substitutes for a real two-institution, real-HTTP isolation test.
9. **Extend the raw-ID-lookup review discipline that closed the last three IDOR bugs to future models without their own `institutionId`.** `StudentFeeAssignment` and (per the original audit, not re-verified this pass) `CertificateRequest` remain schema-level footguns — any new controller code touching them via a bare `findUnique({ where: { id } })` reopens a closed class of bug. Worth a one-line lint rule or PR-review checklist item rather than relying on developer memory each time.

This ordering front-loads the two issues most likely to surprise someone (the Permission Matrix silently not working, and the two portals whose error-state fix regressed relative to their siblings), then works down through verification debt and hygiene. The database/tenant-isolation core, the four Super Admin controllers, and the cross-portal service-layer wiring — the bulk of the old Phase 2 backlog — are, on the evidence gathered this pass, genuinely done.
